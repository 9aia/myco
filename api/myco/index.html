myco — project management, grown not built. A mycorrhizal network for your agents: tasks, signals, handoffs.

Agent-first PM: markdown in project/ is canonical and human-editable; every deterministic write goes through this CLI (auto-commit per verb, --json everywhere). The skill teaches agents the verbs; myco manifest/myco schema are the self-describing surface.

Phase 6 wires continuity — handoff/resume over append-only handoffs/<ID>.md files (one per item, any kind); sepia hooks call them at session boundaries. Phase 7 lands the Jira-parity slice — epic:/ms: item metadata + grouping views, absorb importers (comment sweep, Jira CSV, GitHub dumps). P-007 makes the verb surface data: one registry table drives the clap tree, manifest, and serve/batch dispatch; [verbs] in myco.toml declares repo/user verbs.

continuity 🔒
myco handoff / myco resume / myco interrupt — the continuity trio. At session end handoff appends a ## <today> · <actor> entry plus note to handoffs/<ID>.md (append-only, one file per item, uniform across kinds). At session start resume emits the minimal restart context — the item, its blocks: dep titles, the latest handoff entries, the open checklist — sized for a prompt, the single-item counterpart of status --prompt. interrupt is the abnormal end: a work-state item (claimed/in-progress/blocked) reverts to open and gets an interrupted handoff in one commit.
digest 🔒

movecmd 🔒
myco item move — the cross-repo transfer. The item is re-created in the destination ledger’s own id sequence (kind, title, body, pri/owner/#label/epic/ms carried; blocks: dropped — it names source-ledger ids), both ledgers get a provenance handoff (moved from/moved to), then the source walks to done: a file-backed item keeps its file with status done; a task’s line leaves the ledger and its handoff file drops to handoffs/archive/ — the check-prescribed home for items that are gone. Two commits, one per worktree, both under the usual --no-commit/$MYCO_NO_COMMIT rules.
next 🔒
myco next — the single highest-priority open item: “what should I work on” (I-020, falls out of P-006). It’s a view eval with limit = 1 — the filter flags are view’s [FilterFlags] merged over an open tasks+issues default. --claim is the only new surface: it mutates the emitted item to claimed + an owner in one per-verb commit.
ops 🔒
Re-export — lives in myco_ops::ops so other front-ends (myco-driver) share it. store_at is cli-local: the concrete MdStore factory — myco-ops is generic over myco_store::Store, so the composition root (this crate) names the impl.
org 🔒
myco org — cross-repo scaffolding; cross-repo views are index-sourced myco view specs (view org-board / view org-status, --source index).
plan 🔒
myco plan new|list — execution plans in plans/pl-NNNN-<slug>.md with a phase checklist.
proposal 🔒
myco proposal new|list|status — design proposals in proposals/proposal-NNNN-<slug>.md.
registry 🔒
The single verb registry (P-007) — one VERBS table drives all three front-ends: the clap command tree (command, builder mode, no derive), manifest().verbs/implemented (manifest_verbs), and serve/batch dispatch (crate::serve::Server::dispatch). A verb can’t exist on one surface and not the others: cli/wire handlers share one params schema — the wire schema and the CLI surface are one declaration decoded into the same Args bag.
report 🔒
myco report — aging + velocity + blocked, the “how is the ledger trending” view.
schema 🔒
myco schema — the file/state spec as machine-readable JSON.
serve 🔒
myco serve — a sequential request/response verb surface for embedding: an orchestrator (peregrin) spawns one long-lived process per repo instead of one spawn per verb. A single process serializes writes — no index.lock races — and the store is re-opened per request, so the served process always sees on-disk truth.
status 🔒
myco status [--prompt] — the ledger digest; THE agent-context verb. Human output is compact counts + the in-progress and blocked lists; --prompt is a token-sized block (repo, counts one-liner, then items grouped in-progress → blocked → claimed → open-by-priority, one per line, no prose); --json is the structured digest — with --prompt it’s {"prompt": "<block>"}.
templates 🔒
Item-file body templates — embedded format! strings, not a templating engine. Four kinds, four static skeletons; pulling in minijinja + a myco-template crate would add a dependency for nothing these can’t do. Revisit when templates grow variants (epics, milestones).
todo 🔒
myco todo add|done|defer|list — task items in TODO.md.
view 🔒
myco view [NAME] — declarative views (P-006): named presets from [views] config + built-ins, or an ad-hoc spec from flags. One engine: filter → group → sort → limit → format. Read-only — the write path stays item set/todo/issue.
